# Homebrew tap — maintainer reference

The tap lives at <https://github.com/john-nash-rs/homebrew-tap>. It is created
and initialised; this file documents what a maintainer needs to know.

## State

| Item | Value |
|---|---|
| Repository | `john-nash-rs/homebrew-tap` (public) |
| Default branch | `main` |
| Cask location | `Casks/captaincode.rb`, generated per release |
| Source of truth | [`../.goreleaser.yaml`](../.goreleaser.yaml) |

`Casks/` currently holds only a `.gitkeep`. The real cask is generated by
GoReleaser when a release is published; nothing should be hand-edited or
hand-committed there.

## Publishing the cask

GoReleaser's `homebrew_casks` block pushes the cask on every release. Because
the tap is a **separate repository**, the workflow's automatic `GITHUB_TOKEN`
cannot write to it — that token is scoped to the repository running the
workflow.

A token with write access to the tap is therefore required. Create a
fine-grained personal access token:

- **Repository access:** `homebrew-tap` only
- **Permissions → Contents:** Read and write
- Nothing else, no other repositories

Add it as a secret on the **captaincode** repository, not on the tap:

```sh
gh secret set HOMEBREW_TAP_TOKEN --repo john-nash-rs/captaincode
gh secret list --repo john-nash-rs/captaincode
```

> **The secret is named `HOMEBREW_TAP_TOKEN`, not `GITHUB_PERSONAL_AUTH_TOKEN`.**
> Several GoReleaser guides suggest `GITHUB_PERSONAL_AUTH_TOKEN` for cross-
> repository publishing, but GitHub reserves the `GITHUB_` prefix for its own
> secrets and rejects the name outright:
>
> ```
> HTTP 422: Secret names must not start with GITHUB_.
> ```
>
> Do not rename it back.

Without this secret, releases still publish normally. Only the cask update is
skipped, and the workflow prints the path to the generated file.

## Publishing manually

If a release published without the token, copy the generated cask and push it:

```sh
git clone https://github.com/john-nash-rs/homebrew-tap.git
cp /path/to/captaincode/dist/homebrew/Casks/captaincode.rb \
   homebrew-tap/Casks/captaincode.rb
cd homebrew-tap
git commit -am "Update cask to vX.Y.Z"
git push
```

Note the `.gitignore` in the tap ignores `Casks/*.rb`; use `git add -f` if the
file is not picked up.

## Verifying a published cask

```sh
brew tap john-nash-rs/tap
brew update
brew info captaincode
brew reinstall john-nash-rs/tap/captaincode
captaincode version
captaincode doctor
```

## Why a cask and not a formula

GoReleaser deprecated formula generation (`brews`) in v2.16 and states that
casks should be used instead, including for prebuilt binaries. CaptainCode
ships a bare executable in a tarball, which a cask installs through its binary
stanza. The user-facing command is identical either way.

## Why the cask has no dependencies

The cask deliberately declares no `depends_on`.

- **macOS** uses `/usr/bin/sandbox-exec`, which ships with the operating
  system. There is nothing to install.
- **Linux** requires `bubblewrap`, which a macOS cask cannot install or
  guarantee.

Claiming a `bubblewrap` dependency would be false on both counts: wrong for
macOS, and unverifiable for Linux. The README documents the Linux requirement
instead.
